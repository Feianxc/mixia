# 密匣 Mixia 协议规范 v1

本文是 TS 客户端（`packages/core`）与 Go 服务端（`server/`）的契约。**协议未经第三方密码学审计**。

## 0. 约定

- 二进制在 JSON 中用 base64url 无填充，下文记 `b64`。
- 文本 UTF-8。时间戳为 Unix 毫秒。
- `SHA256` 用于账本与请求（服务端需计算）；`KDF(key, label)` = BLAKE2b-256，`key` 为密钥，`label` 为 UTF-8 消息。
- AEAD = XChaCha20-Poly1305-IETF，nonce 24 字节随机。
- 口令派生 = Argon2id，下限 `ops>=3, mem>=64MiB`，低于下限的头部一律拒绝（防降级）。

## 1. 密钥派生

```
恢复码 rc（25 字节随机，显示为 Crockford base32 40 字符 + 4 字符校验）
rootSignSeed = KDF(rc, "mixia/root-sign/v1")   → Ed25519
rootBoxSeed  = KDF(rc, "mixia/root-box/v1")    → X25519

设备身份种子 seed（32 字节随机）
devSignSeed = KDF(seed, "mixia/dev-sign/v1")   → Ed25519
devBoxSeed  = KDF(seed, "mixia/dev-box/v1")    → X25519

authPub   = P-256 未压缩点 65 字节
deviceId  = b64(SHA256(authPub)[0:16])          （22 字符，绑定认证公钥）

unlockKey = KDF(deviceSecret, "mixia/unlock/v1\n" || Argon2id(passphrase, salt))
keyCommit = KDF(VK, "mixia/vk-commit/v1\n" || vaultId || "\n" || gen)
```

## 2. 信任账本

线上格式：

```json
{ "body": "<b64 of UTF-8 JSON>", "sig": "<b64 Ed25519 签名>" }
```

签名消息：`"mixia/ledger/v1\n" || bodyBytes`。条目哈希：`SHA256(bodyBytes)`，记 `b64`。
**签名针对原始字节**，两端都不需要 JSON 规范化。

body：

```json
{ "v":1, "seq":0, "prev":"", "ts":1730000000000, "signer":"root", "type":"genesis", "data":{} }
```

| type | data | 允许的签名者 |
|---|---|---|
| `genesis` | `ownerId, rootPub, recoveryBoxPub` | root（自签，seq=0，prev=""） |
| `device_add` | `deviceId, name, platform, level, role, authPub, signPub, boxPub, vaults[]` | root / admin |
| `device_revoke` | `deviceId, reason` | root / admin |
| `grant` | `deviceId, role, vaults[]`（整体替换） | root / admin |
| `vault_add` | `vaultId, gen:1, keyCommit` | root / admin |
| `vault_rotate` | `vaultId, gen, keyCommit, snapshotCount, snapshotHash, logHead` | admin（只能走 rotate 接口） |
| `vault_delete` | `vaultId` | root / admin |
| `root_rotate` | `rootPub, recoveryBoxPub` | root（只能走 root/rotate 接口） |

`level` ∈ `hardware|os|software`，`role` ∈ `admin|member`。`vaults` 为 vaultId 字符串数组。

校验规则（**客户端和服务端都必须执行**）：

1. `v==1`；`seq` 连续；`prev` 等于前一条目哈希；seq=0 时 `prev==""` 且 type 必须是 genesis。
2. `signer=="root"` 用当前 rootPub 验签；否则 signer 必须是**未撤销且 role=admin** 的设备，用其 signPub 验签。
3. `genesis`、`root_rotate` 只能由 root 签。genesis 只能在 seq=0 出现。
4. `device_add`：deviceId 不存在且等于 `b64(SHA256(authPub)[0:16])`；role/level 合法；vaults 均已存在。
5. `device_revoke` / `grant`：目标存在且未撤销。不能撤销或降级**最后一个**活跃 admin，除非签名者是 root。
6. `vault_add`：vaultId 不存在，gen=1。`vault_rotate`：库存在且 gen=当前+1。`vault_delete`：库存在。
7. 已撤销的设备不能恢复；deviceId 不可复用。

**两端一致性是安全要求，不只是整洁问题**：账本只能追加，一条服务端接受而客户端拒绝的条目，会让所有
客户端永久无法重放账本。所以服务端必须至少和客户端一样严格：`body` 必须是合法 UTF-8；Ed25519 语义与
libsodium 一致（拒绝小阶点和非规范公钥）；`keyCommit`、`snapshotHash` 解码后恰好 32 字节。

客户端额外钉住：

- 创世哈希（配对时从 offer 获得，或由恢复码派生的 rootPub 比对）。
- 本地 `headSeq/headHash`。拉取时从 `headSeq` 开始（含），若该条目哈希不符或服务器 head 小于本地 → **回滚/分叉告警，停止写入**。

## 3. 请求认证

每个需要认证的请求带：

```
X-Mx-Device: <deviceId> | root
X-Mx-Ts:     <unix ms>
X-Mx-Nonce:  <b64 16 字节>
X-Mx-Body:   <hex SHA256(body)>
X-Mx-Sig:    <b64>
```

签名串（UTF-8）：

```
MIXIA-REQ-1\n{METHOD}\n{PATH?QUERY}\n{TS}\n{NONCE}\n{X-Mx-Body}
```

服务端先验签再读 body，读完比较哈希，不等返回 401。这样匿名请求没法让服务器缓冲大文件。

- 设备：ECDSA P-256 + SHA-256，签名为原始 `r||s` 64 字节，公钥取账本 `authPub`。不要求低 S：ECDSA 可塑性在这里没有影响，重放由 nonce 阻止。
- root：Ed25519，公钥取当前 rootPub。只用于第 7 节标注 `root` 的接口。
- 服务端拒绝：`|now-ts|>300s`、`ts<服务启动时间-5s`、nonce 重复（内存保留 10 分钟）、设备未知或已撤销。

## 4. 变更（云库日志）

服务器视角：

```json
{ "seq":123, "id":"<changeId 22 字符>", "device":"<deviceId>", "gen":1, "blob":"<b64>" }
```

`seq` 与 `device` 由服务器写入（device = 已认证设备，不信任客户端自报）。`blob` 对服务器不透明。

blob 解码后为 JSON `{ "h":b64, "n":b64, "c":b64, "s":b64 }`：

- `h` 头部 JSON：`{v:1, vaultId, gen, changeId, device, counter, ledgerSeq}`
- `c` = AEAD(VK_gen, 载荷, nonce=n, aad=h 的字节)
- `s` = Ed25519(device signSeed, `"mixia/change/v1\n" || h || n || c`)

载荷 JSON：

```json
{ "kind":"item|folder|view|meta", "obj":"<objId>",
  "ver":{"id":"<changeId>","parents":["..."],"ts":0,"device":"..."},
  "del":false, "data":{} }
```

客户端接受一条变更的条件：

1. 外层 `id/device/gen` 与头部一致，`vaultId` 为当前库。
2. `gen` 等于账本中该库的当前代（历史代只在其代内有效，换钥后已被压缩删除）。
3. 作者存在于账本，签名有效。
4. `(device, gen)` 的 `counter` 严格 +1。跳号 = 服务器隐瞒，重复 = 重放 → 告警并停止写入。
   快照变更 `counter` 也从 1 开始，属于执行换钥的设备。
5. AEAD 解密成功。
6. 头部的 `ledgerSeq` 不高于本机账本序号。更高说明账本有尾部没给我：重新拉取一次，仍然更高则
   告警 `ledger_withheld`。这是设备之间互证，用来发现服务器向某台设备隐瞒撤销记录。

冲突：版本 DAG 中同一对象有多个头 → 显示冲突，用户选择或合并后写入一个以多个头为 parents 的新版本。
**整条目为单位**，不做字段级合并，不按时钟覆盖。删除是 `del:true` 的墓碑版本，同样参与冲突判定。

## 5. 库密钥封装

`wrapped = crypto_box_seal(VK, boxPub)`。设备解封后**必须**用账本里的 `keyCommit` 校验，否则拒绝
（防止服务器替换为自己生成的密钥）。恢复封装的 deviceId 固定为 `recovery`，接收方是账本中的 `recoveryBoxPub`。

## 6. 换钥（同时是日志压缩）

管理设备：

1. 同步到最新，记下看到的日志位置 `logHead`。
2. 生成 VK_{g+1}，对每个对象的当前版本（含冲突的所有头、最近 K=20 条历史版本；已永久删除的对象只留墓碑）
   用新密钥重新封装为快照变更。
3. `snapshotHash = b64(SHA256(concat(utf8(id) || blobBytes)))`，按快照顺序，`blobBytes` 是 `blob` 解码后的字节。
4. 调用 `POST /v1/vaults/{id}/rotate`。服务端校验后原子地：追加账本条目、写入新封装、删除全部旧日志和旧封装、写入快照。
   - `logHead` 不等于当前 head → 409 `stale_snapshot`，什么都不变，客户端重新同步后重试。这防止换钥吞掉并发上传的修改。
   - 快照哈希不符、封装没覆盖全部有权设备和 `recovery` → 400。旧日志一旦删除就回不来，服务端要把最后一道关。

其他客户端发现账本 gen 变化后：清空本地该库日志，从 `base` 全量拉取，校验前 `snapshotCount` 条的哈希，
然后把**待发送队列和本机所有不在快照里的头版本**用新密钥重新封装发出。本机绝不因为一份快照而丢弃用户写过的内容。
转发的版本 `device` 改为本设备，以和签名一致。

管理设备总是持有全部云库：新建云库时授权给所有管理设备，批准管理设备时授予全部云库。这样任何一台管理设备都能完成撤销后的换钥。

撤销设备 = 账本 `device_revoke` + 对其可访问的每个云库执行换钥。这样旧设备读不到新内容。

## 7. HTTP API

响应一律 JSON（附件下载除外）。错误：`{"error":"<code>"}`。

认证列：`-` 无；`dev` 任一活跃设备；`acc` 对该库有访问权的活跃设备（admin 也必须在 `vaults` 内）；
`adm` 活跃 admin 设备；`root` 表示也接受 root 认证；`pair` 配对令牌。

| 方法 路径 | 认证 | 说明 |
|---|---|---|
| `GET /healthz` | - | `{"ok":true}` |
| `GET /v1/info` | - | `{"proto":1,"time":ms,"bootstrapped":bool}` |
| `POST /v1/bootstrap` | 一次性令牌 | body `{token, entries:[...], keys:[{vaultId,deviceId,gen,wrapped}]}`。首条必须是 genesis；成功后永久 410 |
| `GET /v1/ledger?from=N` | dev/root | `{entries:[{body,sig}],head:seq}`，N 含 |
| `POST /v1/ledger` | adm/root | `{entries:[...]}`，逐条校验后原子追加；seq 不符 409 `{error:"ledger_conflict",head}` |
| `POST /v1/pair` | adm | `{pairId,tokenHash,expiresAt,offer}`；TTL ≤15 分钟，最多 3 个未完成 |
| `GET /v1/pair/{id}` | pair | `{offer,status,grant}` |
| `POST /v1/pair/{id}/request` | pair | `{request}`，只能一次 |
| `GET /v1/pair/{id}/admin` | adm | `{status,request}` |
| `POST /v1/pair/{id}/grant` | adm | `{grant}` |
| `DELETE /v1/pair/{id}` | adm | 销毁 |
| `GET /v1/vaults/{id}/changes?after=S&limit=500` | acc/root | `{changes:[...],head,base,gen}`；`after<base-1` 时只从 base 返回，客户端据 base 判定需全量重同步 |
| `POST /v1/vaults/{id}/changes` | acc | `{changes:[{id,gen,blob}]}` → `{accepted:[{id,seq}],head}`；按 id 幂等；gen 不是当前代 409 `stale_gen` |
| `GET /v1/vaults/{id}/keys` | acc/root | `{keys:[{gen,wrapped}]}`；root 取 `recovery` 的封装 |
| `PUT /v1/vaults/{id}/keys` | adm/root | `{keys:[{deviceId,gen,wrapped}]}` |
| `POST /v1/vaults/{id}/rotate` | adm | `{entry:{body,sig},keys:[...],changes:[{id,gen,blob}]}`，原子执行，见第 6 节 |
| `POST /v1/root/rotate` | root | `{entry:{body,sig},keys:[{vaultId,gen,wrapped}]}`，原子地换根并替换全部恢复封装，每库恰好一条 |
| `PUT /v1/vaults/{id}/blobs/{blobId}` | acc | 原始字节，上限 50 MiB |
| `GET /v1/vaults/{id}/blobs/{blobId}` | acc | 原始字节 |
| `DELETE /v1/vaults/{id}/blobs/{blobId}` | acc | |
| `GET /v1/audit?limit=100` | adm | `{events:[{ts,device,action,detail}]}`，不含内容 |

配对令牌放在请求头 `X-Mx-Pair-Token: <b64>`，服务端校验 `SHA256(token)==tokenHash`（恒定时间比较）。
错误令牌累计 5 次销毁该配对。匿名接口按 IP 限流（优先 `CF-Connecting-IP`）。

`vault_add` 走 `POST /v1/ledger`，服务端据此建库。库的 `head` 单调递增，换钥后 `seq` 继续增长，`base` 为
最小保留 seq。

## 8. 配对

配对码 24 字符 Crockford base32（120 位）：前 6 字符 `pairId`，后 18 字符 `ps`。

```
K     = KDF(ps, "mixia/pair/key/v1")
token = KDF(ps, "mixia/pair/token/v1")
```

`K`、`token` 的 KDF 密钥是 `ps` 的 18 个 ASCII 字节。`offer`、`request`、`grant` 的编码都是
`b64(nonce || AEAD(K, JSON, aad="mixia/pair/v1"))`。

1. 管理设备生成配对码，`POST /v1/pair`，`offer = AEAD(K, {genesisHash, serverUrl, adminName})`。
2. 新设备输入或扫描配对码 → 取 offer 解密 → **钉住 genesisHash**（服务器不知道 ps，无法伪造）。
3. 新设备生成密钥，`request = AEAD(K, {name, platform, level, authPub, signPub, boxPub})`。
4. 管理设备解密 request，向用户展示名称、平台、等级和指纹，用户选择角色和库范围。
   **指纹覆盖全部三把公钥**，两端屏幕对比一致才能批准。
5. 管理设备写账本 `device_add`，`PUT keys`，`grant = AEAD(K, {deviceId, headSeq, headHash})`。
6. 新设备收到 grant → 用设备密钥认证 → 拉账本校验到钉住的创世哈希 → 校验账本在 `headSeq` 处的哈希
   等于 `headHash`（服务器不能给它看缺了撤销记录的旧分支）→ 校验账本里本机的 `signPub`、`boxPub` 是自己的 →
   取封装 → 校验 keyCommit。

`level` 是设备自报的。Android/TPM 的远程证明未实现：单一所有者亲手批准自己的设备，证明的主要收益
（防被修改的客户端）对此场景有限。界面标注为“自报”，不声称已验证。

## 9. 恢复

账户恢复（所有设备丢失）：输入恢复码 → 派生 root → 以 root 身份拉账本，比对 `rootPub` →
以 root 签名追加新设备 `device_add`（admin）→ 用恢复封装解出库密钥 → 重新封装给新设备 → 建议撤销旧设备并换钥。

## 10. Pack 文件

```
"MIXIAPK1" (8 字节) || 头部长度 u32 LE || 头部 JSON || 密文
```

头部：`{v:1, kind:"backup|cold|transfer", vaultId, gen, createdAt, count, slots:[...]}`。
载荷 = AEAD(packKey, 快照 JSON, aad=头部字节)。头部被 AEAD 认证。

slot 类型：

- `seal`：`{t:"seal", to:"<b64 X25519 公钥>", w:<sealed packKey>}`，用恢复公钥或目标设备公钥封装。备份时不需要输入恢复码。
- `pw`：`{t:"pw", salt, ops, mem, n, w}`，`w = AEAD(KDF(codeBytes, "mixia/cold/v1\n"||Argon2id(pass,salt)), packKey)`，冷库用，要求口令和恢复码都对。

快照 JSON：`{vaultId, name, policy, versions:[...], exportedAt, blobs:{id:b64}}`，版本含完整 DAG 片段，
未知字段原样保留，`blobs` 是本机持有的附件密文，附件密钥在条目里。

**已知限制**：`seal` 槽的接收方公钥是公开的，所以任何人都能伪造一个能被解开的 Pack。冷库（`pw` 槽）不受影响，
口令加恢复码同时构成认证。备份文件要当成重要物品保管，恢复后核对内容；恢复总是生成新的本地库，不会覆盖现有数据。

## 11. 浏览器填充

这一段只在本机，不经过服务器。消息格式和错误码见 `apps/desktop/native/nmhost/README.md`。

扩展 ID `ikicghdoopckcolomkneepiooaengmep`，由 `apps/extension/manifest.json` 的公钥决定，私钥在 `.secrets/extension-key.pem`。
native messaging 主机名 `online.feian.mixia`。

| 操作 | 请求 | 回复 |
|---|---|---|
| `status` | | `state`：`ready` 或 `locked` |
| `list` | `origin` | 匹配的云库条目 `{ref,title,username}`，最多 50 条，没有密码 |
| `fill` | `origin, ref` | `{username,password}`。只接受云库条目，桌面确认后才有 |
| `pick` | `origin` | `{username,password}`。在桌面选账号再确认 |

`ref` 是 `库 ID/条目 ID`。`origin` 是浏览器给的规范形式，带路径、账号或大写字母的都拒绝。多一个字段也拒绝。

`fill` 时桌面重新算一遍站点匹配：拿 A 站点的 `ref` 配 B 站点的 `origin`，不会弹确认框，直接 `no_match`。
确认之后再查一次，等待期间锁定或条目改了网址都不给。

版本演进：这里的回复形状由 host 按操作过滤，新增字段要同时改 `filterReply`，否则回复会被当成坏数据。
