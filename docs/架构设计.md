# 密匣 Mixia 架构设计（v2，基于研究报告 v1.0 优化）

本文是研究报告《个人密码系统架构设计与研究报告 v1.0》之后的工程版架构。报告的安全目标、三类保险库、
威胁模型和“不作出的承诺”全部保留；这里改的是**实现路线和结构**，把报告里 22–38 人周的方案压到
可以真正做完并验证的形态。协议细节见 [协议规范.md](协议规范.md)。

## 1. 相对报告做了哪些调整

| # | 报告方案 | 优化后 | 为什么 |
|---|---|---|---|
| 1 | Rust 核心 + Flutter 界面 + Kotlin/Swift 适配 | TypeScript 核心 + libsodium(WASM) + React 界面，Electron（桌面）/ Capacitor（手机）外壳，硬件能力用很薄的原生层（Go TPM 助手、Java Keystore 插件） | 加密、格式、同步只有**一份实现**，能在 Node 里完整测试；libsodium 是成熟的 C 库。本机已有 Capacitor + Android 跑通的构建路线和 TPM 2.0，手机确认是 Android。Bitwarden 桌面端同样是 Electron |
| 2 | 账户 + 设备批准 + 会话 | **没有账户、没有密码登录、没有会话令牌**。每个 API 请求都由设备硬件密钥直接签名 | 报告指出 Vaultwarden 存在绕过批准的平行登录路径、“单独的 Bearer token 不足以实现强设备约束”。不存在登录，也就不存在绕过登录；服务器上没有任何密码或口令派生物可被撞库 |
| 3 | 设备授权记录、撤销记录、库授权、检查点分别设计 | 合并为一条**信任账本**：哈希链 + 签名，客户端和服务端用同一规则校验 | 一个机制同时解决“服务器伪造设备、扩大范围、重放、回滚”；新设备只需钉住创世哈希 |
| 4 | 三类库 | 保留三类库，但**一个库引擎 + 三种存储策略** | 三类库的差别只在“数据能走哪条路”，不在数据结构。少两套引擎，也少两套漏洞 |
| 5 | 恢复包、离线备份、设备快照、冷库文件各有格式 | **一种 Pack 格式**，按接收方不同（恢复码 / 目标设备 / 口令+恢复码）区分 | 备份、迁移、冷库、设备传输走同一份已测试的代码 |
| 6 | 每库每代密钥 → 记录密钥 → 惰性重加密 | 去掉记录密钥层。换钥时**全量重加密并压缩日志** | 个人规模（1 万条约十几 MB）全量重加密只要几秒，不必维护“哪些记录已换钥”的状态；换钥和日志压缩合并成一个操作 |
| 7 | 管理授权密钥 + 恢复材料分离 | 恢复码直接派生**根密钥**；根密钥平时不落任何设备 | 根是离线的。日常批准由管理设备签名，账本校验其权限来自根 |
| 8 | 云传输放受限进程 | 界面层 CSP `connect-src 'none'`，完全没有联网能力；只有外壳的传输桥能联网，且只连配置的服务器 | 跨平台都能实施的硬边界：界面代码或第三方依赖的任何意外请求都会被浏览器内核拦下 |
| 9 | 网页端做有限管理 | **不做网页端**，服务器不提供任何页面 | 彻底消除“服务器下发恶意 JS”这条路径；代码只来自本机安装包 |
| 10 | 服务器独立实例 | 单文件 Go 服务，仅监听 127.0.0.1，经现有 Cloudflare Tunnel 接入，不开新公网端口 | 参考部署的主机上还有其他公开服务，无法做到操作系统级隔离。因此靠专用用户、systemd 沙箱（含禁止主动外联），以及“服务器被攻破也只拿到密文”这条底线。原计划用独立隧道，但当前 Cloudflare 令牌没有隧道权限，按不扩大权限的原则复用 `personal-blog` 隧道；切换时用临时第二连接器接流量，其他站点没有中断 |

## 2. 总体结构

```
┌──────────────── 可信设备（Windows / Android / …）────────────────┐
│  界面层 React      CSP connect-src 'none'，无联网能力             │
│  ─────────────────────────────────────────────────────────────  │
│  共享核心 @mixia/core（TS + libsodium WASM）                      │
│    账本校验 · 库引擎 · 加解密 · 同步 · Pack · 导入导出            │
│  ─────────────────────────────────────────────────────────────  │
│  云同步库     │ 重要本地库      │ 冷库                            │
│  独立 KV      │ 独立 KV+独立口令 │ 只在内存，文件在离线介质        │
│      │                                                           │
│  ────┼────────────────────────────────────────────────────────  │
│  平台外壳：传输桥（只连配置的服务器，只接受云库）                 │
│            硬件密钥：TPM / Android Keystore / OS 钥匙串           │
└──────┼───────────────────────────────────────────────────────────┘
       │ HTTPS，每个请求设备硬件密钥签名；内容只有密文
       ▼
 Cloudflare Tunnel（不可信中继）→ 服务器 127.0.0.1 → mixia-server（Go 单文件 + SQLite）
   只保存：信任账本 · 密文变更日志 · 按设备封装的库密钥 · 加密附件
```

重要本地库和冷库**没有指向云端的路径**：同步模块拿不到它们的 KV 句柄；账本里没有它们的记录，服务器
不知道它们存在。

## 3. 四个独立判断（沿用报告 6.1）

| 问题 | 机制 |
|---|---|
| 这个请求来自谁？ | 设备硬件密钥（P-256，不可导出）对请求签名，服务器查账本 |
| 这台设备能访问哪些库？ | 账本 `device_add` / `grant` 记录，加上只发给该设备的库密钥封装 |
| 现在可以解密吗？ | 本地口令 + 硬件封存的设备秘密，两者合成解锁密钥。任一缺失都解不开 |
| 原设备没了怎么办？ | 打印的恢复码（根）+ 服务器密文；本地库用自己的恢复码 + Pack 备份 |

## 4. 密钥层次

| 材料 | 作用 | 存放 |
|---|---|---|
| 主口令 | 本地解锁的一个因子 | 只在用户脑中。不上传，服务器上没有它的任何派生物 |
| 设备认证密钥（P-256） | 给每个 API 请求签名 | TPM / Android Keystore，不可导出 |
| 设备秘密（32 字节） | 本地解锁的另一个因子 | 被硬件封存，复制数据目录到别的机器无法解封 |
| 设备身份种子 → Ed25519 + X25519 | 给变更和账本条目签名；接收库密钥 | 本地密钥库，由解锁密钥加密 |
| 根密钥 Ed25519 + 恢复 X25519 | 信任根；账户级恢复 | **不落设备**，由恢复码现场派生 |
| 库密钥（每库每代 32 字节） | 加密该库全部内容 | 云库：封装给每台授权设备和恢复公钥；本地库：本机密钥槽 |
| 恢复码 | 最高权限 | 用户打印 / 离线保存。账户一份，每个本地库各一份，冷库一份 |

被研究报告列为独立层的“记录与附件密钥”：记录直接用库密钥（理由见第 1 节第 6 条），附件保留独立随机
密钥，存在加密后的条目内，大文件因此不必随换钥重写。

## 5. 三类库

| | 云同步日常库 | 重要本地库 | 完全离线冷库 |
|---|---|---|---|
| 适合 | 普通网站、测试账号 | 生产管理员、主邮箱、域名、资金 | 根级恢复材料 |
| 数据路径 | 本地加密 → 服务器 → 授权设备 | 本机；用 Pack 文件或局域网发给指定设备 | 离线介质上的文件 |
| 云端可见 | 不透明 ID、大小、时间 | **无** | **无** |
| 解锁 | 主口令 | 该库独立口令 | 该库口令 + 恢复码 |
| 写入 | 多设备离线读写 | 单主写设备，其他设备只读快照 | 打开文件 → 编辑 → 显式保存 |
| 设备绑定 | 设备秘密 + 封装 | 设备秘密 + 独立口令 | 不绑设备（需要可迁移），靠两因子 |
| 自动填充 | 可以 | 逐次确认 | 不可以 |

**跨库移动**是显式迁移：目标库写入并验证后才删源记录。从云库移回本地不能抹掉历史，会保留
“曾进入云端”的标记，提示用户去原系统改密码。

## 6. 分类体系

- **保险库**：安全边界（决定存储和授权）。
- **文件夹树**：无限层级，表达 项目 / 系统 / 环境。
- **标签**：跨文件夹的横向属性。
- **自定义分组**：保存的筛选条件（如 `tag:生产 type:server`），可跨库，结果始终标明所属库。
- **环境字段**：production / staging / dev 等，独立于目录。

组织属性不改变安全属性：把条目换文件夹不会改变它存在哪里。

### 密钥与 API

API Key、访问令牌、SSH 密钥、证书和环境变量组是条目类型，和登录项走同一套加密、同步和版本逻辑。服务商、到期时间、轮换周期和用途都在加密条目里，服务端和协议没有改动，云端看不到有多少把密钥、属于哪家服务商。

- 到期和轮换状态在本机计算。不向外发请求，也不校验密钥是否仍然有效。
- 机密字段换值时，旧值进入条目历史。历史和条目同库存放，放在云库就会同步到批准的设备。
- 机密字段的值不参与搜索，列表最多显示末 4 位。
- 手机和浏览器的自动填充只取有 `password` 的条目，这些类型默认不出现在候选里。
- 导出到 shell 时按目标语法转义。变量名不合法就跳过，不拼进命令。

## 7. 云端能看到什么

可见：设备公钥和角色、设备名（默认系统类型 + 短 ID，用户可改；**这是明文，别写敏感内容**）、
不透明库 ID、密文大小、时间、IP。

不可见：库名、文件夹、标题、用户名、网址、密码、备注、附件名、搜索词，以及本地库和冷库的存在。

Cloudflare Tunnel 终止 TLS，Cloudflare 与被攻破的服务器处于同一位置：能看到密文和流量模式，无法
解密或伪造。这就是把服务器当作不可信方设计的价值。

## 8. 能防什么、不能防什么

| 场景 | 结果 |
|---|---|
| 服务器数据库被偷 | 只有密文、公钥、封装。没有口令派生物可离线爆破 |
| 服务器被完全控制 | 不能伪造设备或条目，不能解密。**能**拒绝服务、隐瞒最新数据（尾部），客户端检测到回退会告警并停止写入 |
| 服务器被控制**且**与被撤销的管理设备串通 | 见下方“已知边界”。这是目前最强的攻击场景 |
| 主口令泄露 | 没有已批准设备的硬件就没用 |
| 复制设备数据目录 | 设备秘密解封不了，口令也打不开 |
| 设备被盗（已锁） | 需要口令；可在别的设备撤销并换钥 |
| 设备中了恶意软件且已解锁 | **防不住**。这是任何密码管理器的边界 |
| 恶意网页、恶意 iframe 想拿密码 | 拿不到。见第 10 节 |
| 恢复码泄露 | 最高权限泄露，需换根、换钥并轮换实际密码 |
| 全部设备和恢复码都丢失 | **无法恢复**，没有后门 |

### 已知边界

下面这些是独立安全审查指出、经评估后接受或只做了部分缓解的。写在这里是因为它们真实存在。

**服务器和被撤销设备串通，针对一台长期离线的设备做全量隔离。** 服务器如果同时隐瞒账本尾部和所有能暴露更新序号的变更，
被隔离的设备在隔离期间还相信被撤销设备。已有的缓解：设备之间通过变更头互证账本序号；新设备批准时带账本位置；“设备”页
显示账本位置指纹，可以人工比对两台设备是否一致。彻底解决需要服务器之外的独立通道。怀疑时，在两台设备上对比这个指纹。

**本机同用户的恶意程序（应用已锁定时）。** 硬件密钥没有用户认证：同用户进程能调用 TPM 解封设备秘密，再对主口令做离线
爆破，也能用设备身份发请求。硬件防的是“私钥被带走”，不防“当场使用”。所以主口令依然必须够强。安装到 Program Files
让代码目录不可被普通用户改写；装到自定义目录时，安装程序会把所有者改成管理员组、权限收紧成和 Program Files 一样，但数据目录的本地状态（账本、设置）没有逐项认证，这类攻击者还可以改写它们。

**备份文件可被伪造。** 见协议第 10 节。恢复总是生成新库，不覆盖现有数据，恢复后要核对。

**没有代码签名证书。** Windows 会提示未知发布者，更新要手动安装。安装包是否被替换，靠你从自己的渠道获取。

**本机同用户的恶意程序（应用已解锁时）能列出云库账号。** 它可以直接启动 `mixia-nmhost.exe`，管道两端的身份核对挡不住
“同一个程序被别人启动”。这样能查到某个站点的云库标题和用户名，拿密码仍要用户在桌面窗口点确认。

**匹配的站点本身有 XSS 时，填进去的密码它能读到。** 这是所有自动填充的边界，每次填充都要点确认能缩小窗口，不能消除。

**JS 无法可靠清零内存。** 见下一段。

沿用报告 11.2：不承诺绝对安全、离线设备实时撤销、已复制数据远程消失、第三方备份软件绝不复制文件。
JS 字符串无法可靠清零，解锁期间明文会驻留内存，这是相对 Rust 方案确实放弃的一点；对抗的是“已控制
本机的攻击者”，而这类攻击者在解锁状态下本来就能读屏和键盘记录。

## 9. 目录结构

```

packages/core/       共享核心（TS），含全部协议实现和测试
packages/ui/         React 界面（桌面与手机共用）
apps/desktop/        Electron 外壳 + hwkey（Go，TPM 助手）+ nmhost（Go，浏览器扩展的桥）
apps/extension/      Chrome / Edge MV3 扩展
apps/mobile/         Capacitor Android + Java 插件（Keystore、传输、自动填充）

```

## 10. 浏览器填充

```
网页 ── 内容脚本 ──▶ 扩展后台 ──native messaging──▶ mixia-nmhost ──命名管道──▶ mixia-nmhost --serve
        只认登录框     origin 在这里算                过滤操作和回复              │ stdio
                                                                                ▼
                                       渲染进程 BrowserFill（站点匹配、确认）◀─IPC─ Electron 主进程
```

扩展不持有库密钥，也没有 `storage` 权限。它每次只拿到用户在桌面窗口确认的那一条，转给发起请求的文档后就丢掉。

| 问题 | 怎么判断 | 位置 |
|---|---|---|
| 这个页面是哪个站点 | 顶层框架的 URL 来自 `webNavigation`，发送方的 origin 来自浏览器填的 `sender.origin`。内容脚本的消息里除了 `t` 没有参数 | `apps/extension/src/policy.ts` |
| 这个框架能不能填 | 框架和它到顶层之间的每一层都必须与顶层同源。跨源 iframe 不填，同源页面被嵌在别人的框架里不填，沙箱 iframe（浏览器报告 `null`）不填 | `judgeFrame` |
| 这条记录能不能给这个站点 | 解析后的主机名相等，或页面是条目主机的子域。不用子串，不反向匹配父域。见下表 | `packages/core/src/autofill.ts` |
| 用户同意了吗 | 每次填充都在桌面窗口确认，弹出后 0.7 秒内不可点，60 秒没动作按拒绝 | `packages/core/src/browserfill.ts` |
| 确认期间页面变了吗 | 文档 ID 和框架判断在发送前重新核对，密码按 `documentId` 只发给那个文档 | `apps/extension/src/controller.ts` |
| 字段看得见吗 | 隐藏、透明、移出屏幕的字段不填 | `apps/extension/src/content.ts` |

站点匹配的细节：

| 情况 | 结果 |
|---|---|
| `example.com` 对 `https://login.example.com` | 给，确认框提示是子域名 |
| `login.example.com` 对 `https://example.com` | 不给，父域不反向匹配 |
| `example.com` 对 `http://example.com` | 不给，明文页面可能被中间人塞表单。要给就在条目里写 `http://` |
| 条目写了端口 | 只认这个端口；没写只认默认端口 |
| 单段主机、IP、`co.uk` 这类公共后缀、`github.io` 这类多租户后缀 | 只精确匹配，不做子域匹配。后缀列表不完整，只覆盖常见的 |
| 手机推荐（系统只给域名，没有协议和端口） | 同一套规则，按 https 默认端口算：写了非默认端口的条目不推荐；页面其实在非默认端口时分辨不出。见 `phoneOrigin`、`packages/core/src/phonefill.ts` |

三类库：

| | 进扩展弹窗 | 怎么填 |
|---|---|---|
| 云库 | 匹配的条目显示标题和用户名 | 弹窗点选，桌面确认 |
| 重要本地库 | **不进**，标题和用户名不离开桌面窗口 | 弹窗点“在桌面端选择”，在桌面选中后逐次确认。扩展直接拿 ref 来要也会被拒 |
| 冷库 | 不进 | 不可以。桌面候选里也没有 |

选择层用浏览器自己的扩展弹窗，不用页内 iframe：页面盖不住也嵌不进去，扩展没有 `web_accessible_resources`，所以网页探测不到、嵌入不了。
弹窗失去焦点就会关闭，所以等确认和填入都在后台做。

本机这一段的边界：`allowed_origins` 钉死扩展 ID，host 自己再核对启动参数。管道 DACL 只有当前用户，拒绝远程客户端，两端核对
对方是不是同一个程序。管道上只有 `status`、`list`、`fill`、`pick` 四个操作，浏览器一侧、管道服务、Electron 主进程、渲染进程各校验一次。
